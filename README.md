# database-recovery-catalog-atomicity-validator
验证恢复目录、检查点和日志指针的原子更新

> **注意:本项目中所有对象存储、WAL 段、基础备份、摘要清单均为内存中的模拟对象,
> 不访问任何真实的数据库、文件系统或对象存储服务。**

## 背景

恢复目录更新写到一半时数据库崩溃:部分记录指向新文件,部分仍指向旧文件,
而任何单独一条记录看起来都合法。`catalog_validator.py` 实现了一个
恢复目录原子性验证器,根据目录版本、双指针、检查点、WAL 段、基础备份、
摘要清单和更新事务,判断哪个目录版本构成完整的恢复点。

核心原则:**目录更新必须与文件持久化边界(fsync)一致**,
不能只依赖目录记录中的时间戳判断合法性。

## 判定规则

- **双指针一致性**:主/镜像指针不一致说明目录切换在落盘途中被中断,
  只允许回退到镜像(旧)一侧双方都曾确认的版本。
- **旧指针回退**:双指针一致但低于已提交高水位,视为旧副本覆盖,拒绝回退。
- **持久化边界**:目录引用的每个文件必须在其所属事务中完成 fsync,
  否则视为部分写入。
- **摘要完整性**:引用文件必须出现在摘要清单中且摘要一致,缺失即阻止。
- **交叉引用**:目录版本只能引用本事务或已提交旧版本事务写入的文件;
  指向更新/未提交事务的文件视为双版本交叉引用。
- **WAL 连续性**:从检查点 WAL 起点到版本 `wal_end` 必须被 WAL 段连续覆盖。
- **基础备份**:检查点必须关联存在的基础备份,且备份对应版本不晚于目录版本。

## 输出

`validate()` 返回 `ValidationReport`:

- `recoverable_version`:构成完整恢复点的目录版本(无则为 `None`)
- `orphaned_objects`:已持久化且有摘要、但未被可恢复目录引用的孤立对象
- `blocking_reasons`:指针级与版本级的阻止原因
- `version_status`:每个目录版本各自的检查失败原因

## 运行测试

```bash
python -m unittest
```

测试覆盖:目录切换中断、双版本交叉引用、WAL 缺失(尾部缺失与中间空洞)、
旧指针回退、部分写入、摘要缺失、孤立对象识别与正常恢复路径。
兼容 Python 3.8.2+。
